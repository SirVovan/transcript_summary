# Слой 2: Виджет

## Назначение

Конвертировать мастер-MD в HTML-виджет напрямую.

Принцип: механический перенос без редакции. Весь контент мастер-MD переносится без потерь — левая колонка = полный `### Текст`, правая колонка = полный `### Карта`.

---

## Шаг 1. Запустить генератор на мастер-MD

```
PYTHONUTF8=1 python "$HOME/.claude/skills/konspekt/widget_generator.py" "<рабочая-папка>/MASTER_[Название].md"
```

`<рабочая-папка>` — папка серии в воркспейсе (например, `konspekts/<серия>/`) или папка урока. Скрипт сам парсит мастер-MD, собирает HTML, проверяет JS-синтаксис. Ожидаемый результат: `✅ JS syntax OK` и путь к созданному `WIDGET_[Название].html`.

При ошибках парсинга — сообщение вида `Ошибка парсинга мастер-MD: [причина]`. Чаще всего причина — отклонение мастер-MD от ожидаемой структуры (нет `### Карта`, не разобран заголовок сегмента и т.п.). Исправить мастер-MD и перезапустить.

---

## Шаг 2. Проверить виджет

1. Открыть HTML в браузере
2. Первый экран — «Логическая реконструкция» с абзацем, блоком «Главная идея» и таблицей (если сегментов > 1)
3. Кнопка «Далее» ведёт к Сегменту 1
4. Левая колонка каждого сегмента = полный `### Текст`
5. Правая колонка = все карточки из `### Карта`
6. Специальные блоки (Лайфхак/Важно/Демонстрация/Принцип/Критерии…) с цветной левой рамкой
7. Промпт-блоки моноширинные, с кнопкой «копировать»

## Резервный путь: JSON

Если нужно тонко допилить виджет руками без правки мастер-MD — можно собрать JSON напрямую и запустить:

```
PYTHONUTF8=1 python "$HOME/.claude/skills/konspekt/widget_generator.py" "<рабочая-папка>/WIDGET_[Название].json"
```

Формат JSON — см. структуру эталонного файла виджета в любой папке `konspekts/<серия>/`. Правила mapping мастер-MD → JSON (метки блоков → цвета, типы сегментов, шаблон `.pr-block`) описаны ниже в разделах «Конвертация body», «Конвертация right», «Блок промпта» — они применимы и при ручной сборке, и описывают то, что делает парсер автоматически.

## Конвертация `body` (### Текст → HTML)

Каждый абзац прозы → `<p>текст</p>`

`**текст**` → `<strong>текст</strong>`

Маркированный список:
```
- пункт А
- пункт Б
```
→
```html
<ul style="margin:4px 0 9px 18px;padding:0"><li style="margin-bottom:4px">пункт А</li><li style="margin-bottom:4px">пункт Б</li></ul>
```

Нумерованный список:
```
1. пункт А
2. пункт Б
```
→
```html
<ol style="margin:4px 0 9px 18px"><li style="margin-bottom:4px">пункт А</li><li style="margin-bottom:4px">пункт Б</li></ol>
```

Специальные блоки `> **Метка:** ...` (включая многострочные с переносами и списками внутри).

**Цвет по смыслу метки** — соответствует трём уровням (И)/(М)/(Д) из Карты:

| Метка | Уровень | Цвет | bg / border |
|---|---|---|---|
| **Ключевая идея**, **Принцип**, **Лайфхак** | (И) идея | синий | `#ECF2FB` / `#2562B0` |
| **Методология**, **Критерии**, **Шаг N. Финальная формулировка**, **Правило**, **Шаблон** | (М) метод | зелёный | `#EBF5EB` / `#2E6E2E` |
| **Пример**, **Пример декомпозиции**, **Демонстрация**, **Важно** | (Д) конкретика | оранжевый | `#FAF0E4` / `#96580F` |

Если метка не из таблицы — определи уровень по смыслу: формулирует **идею** → синий; задаёт **правило/проверку/шаблон** → зелёный; показывает **конкретный пример/предупреждение** → оранжевый.

**Шаблон HTML** (подставить bg/border из таблицы):

```html
<div style="background:[bg];border-left:3px solid [border];border-radius:0 8px 8px 0;padding:8px 12px;margin:6px 0;font-size:12.5px;line-height:1.55"><strong>[Метка]:</strong> [содержимое — может включать <br>, <ul>, <ol>]</div>
```

Многострочный блок (с вложенным нумерованным списком) — собирать в один `<div>`:

```markdown
> **Критерии хорошей идеи:**
> 1. Вам лично это интересно.
> 2. Кому-то это нужно.
> 3. Это реально сделать.
```
→
```html
<div style="background:#EBF5EB;border-left:3px solid #2E6E2E;border-radius:0 8px 8px 0;padding:8px 12px;margin:6px 0;font-size:12.5px;line-height:1.55"><strong>Критерии хорошей идеи:</strong><ol style="margin:6px 0 0 18px"><li>Вам лично это интересно.</li><li>Кому-то это нужно.</li><li>Это реально сделать.</li></ol></div>
```

## Блок промпта (`> **Промпт «...»:**` или `> **Скрипт «...»:**` + fenced code block)

В мастер-MD промпт оформляется так:

````markdown
> **Промпт «Название»:**

```
текст промпта дословно
с переносами строк
```
````

Метка может начинаться со слова `Промпт` или `Скрипт` — парсер принимает оба и рендерит метку как есть (`Скрипт` уместен для речевых заготовок: скриптов звонка, пулов вопросов).

В виджете → отдельный блок `.pr-block` с моноширинным шрифтом и кнопкой «копировать». **Не** превращать в обычный blockquote-блок: промпты — это код, который пользователь копирует в нейросеть, форматирование критично.

**Шаблон HTML** (id промпта — `p1`, `p2`, ... сквозной по виджету; `[ТЕКСТ_ПРОМПТА]` — с экранированными кавычками `&quot;`, перенос строк сохраняется как `\n` внутри JSON-строки, CSS `white-space:pre-wrap` сохранит их при рендере):

```html
<div class="pr-block"><div class="pr-head"><span class="pr-label">Промпт · Название</span><button class="pr-copy" id="cpbp1" onclick="cp('p1')">копировать</button></div><div class="pr-text">[ТЕКСТ_ПРОМПТА]</div></div>
```

Кнопка «копировать» обслуживается готовой функцией `cp(id)` в движке — id передаётся как строка, она ищет `#cpb<id>` и копирует текст из соседнего `.pr-text`.

**Внутри `pr-text`** — никаких HTML-преобразований текста промпта (никаких `<strong>`, никаких `<br>`). Только сам текст промпта дословно, с экранированием HTML-спецсимволов (`&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`). Переносы строк — буквальные `\n` в JSON, рендерятся через CSS `white-space:pre-wrap`.

## Конвертация `right` (### Карта → HTML)

Каждый буллет `### Карта` → одна insight-карточка. Все буллеты без исключения.

Цвет `border-left-color` по типу сегмента: `concept` → `#2562B0`, `method` → `#2E6E2E`, `demo` → `#96580F`

```markdown
- **Термин:** пояснение
- **Другой:** другое
```
→
```html
<div class="insights"><div class="insight" style="border-left-color:#2562B0"><strong>Термин:</strong> пояснение</div><div class="insight" style="border-left-color:#2562B0"><strong>Другой:</strong> другое</div></div>
```

---

## Технические ограничения

- Никаких `var()` в inline-стилях — только хардкод hex-цветов
- JSON-строки однострочные — никаких литеральных переносов строк внутри значений
- Кавычки в HTML-атрибутах → `&quot;`

## Opt-in ветка: виджет с кадрами

Триггер — явная команда «сделай виджет **с кадрами** из X». Без этой команды всё выше (Шаги 1–2) работает без изменений; ветка — надстройка поверх обычной сборки, не замена.

Задача ветки: найти в видео ключевые кадры (слайды, промпты на экране, инфографику), вписать их в HTML-виджет — текстом (промпт/тезис слайда) или картинкой (иллюстрация/схема/скрин интерфейса).

### Шаг 0. Вход: откуда видео

- **URL** — из шапки транскрипта, поле `source:` (см. `source_passport.py`) → канонический watch-URL.
- **Локальный файл** — mp4/webm, указанный в команде или лежащий рядом с транскриптом.
- Ни того ни другого нет → мягкая деградация (см. Шаг 6): собрать обычный виджет без кадров.

### Шаг 1. Кандидаты и contact-sheet (`frames_extract.py`)

```
PYTHONUTF8=1 python "$HOME/.claude/skills/konspekt/frames_extract.py" extract \
  --url "<youtube-url>" --srt "<рабочая-папка>/SRC_....srt" \
  --master-md "<рабочая-папка>/MASTER_[Название].md" \
  --work-dir "<рабочая-папка>/frames_work" [--threshold 0.2]
```

Вместо `--url` можно `--video <путь>` (флаги взаимоисключающие, один обязателен). Остальные флаги: `--srt` (транскрипт, обязателен — источник transcript-cues и маркеров), `--master-md` (мастер-MD, обязателен — источник границ сегментов для посегментных квот и привязки кадр→сегмент), `--work-dir` (папка для кадров и простыней, обязателен), `--threshold` (порог ffmpeg scene-detection, по умолчанию `0.2`). Подкоманда `extract` завершается на простынях+манифесте — триаж/отбор идут отдельными шагами ниже.

Под капотом: `download_video` (yt-dlp, кэп 720p) скачивает видео во временную `frames_work/`; `scene_timecodes` (ffmpeg scene-detect + `showinfo`) объединяется с `cue_timecodes` (мягкие подсказки в транскрипте — `CUE_MARKERS`: «смотрите», «на слайде», «скопируйте» и т.п., без гарантии нарезки, см. ниже про маркеры); `segment_bounds` разбирает границы сегментов из мастер-MD, и `bucket_timecodes` бакетирует таймкоды по сегментам, применяя `dedup_by_gap` **внутри каждого сегментного бакета** (посегментный cap) с общим предохранителем ~150 (единый нисходящий cap для всех бакетов при переполнении); `extract_frame` вырезает по кадру на таймкод (`cand_0001.png`, `cand_0002.png`, …); после извлечения `phash_dedup` (average-hash, скользящее окно N=3) гасит повторные каты камеры. Порог scene-detect по умолчанию понижен до 0.2 (подбирается на E2E — возросший шум гасит pHash). `contact_sheet` (PIL) собирает пронумерованную общую простыню `contact_sheet.png`, а также по одной посегментной `contact_sheet_seg<NN>.png` на каждый сегмент (вход Яруса 2, см. Шаг 2.5). Видео — временное, удаляется после нарезки; кадры-кандидаты кэшируются.

**Маркеры «заскриньте» — отдельная, гарантированная категория.** Узкий явный список `MARKER_TRIGGERS` (`скринь`, `зафиксируй`, `сохрани этот`) — это **не** `CUE_MARKERS` выше, а прямой призыв спикера сохранить кадр. `marker_timecodes` находит такие реплики и возвращает `{timecode, phrase}`. Кадр на секунде маркера режется **вне** `dedup_by_gap` и вне пересчёта cap в `bucket_timecodes`: его не может поглотить соседний scene-cut и не может срезать ужатие потолка при переполнении. На серию слайдов после маркера (например «5 ошибок» — несколько слайдов подряд) `expand_marker_window` добавляет к якорному кадру ещё кадры на scene-change'ах внутри окна `marker_window_sec` после маркера (дефолт 100 с, но не далее следующего маркера), всего не более `marker_window_frames` кадров на маркер (дефолт 5, включая якорный). Маркерные кадры проходят триаж как и все остальные (получают `type`/`confidence`), но результат триажа не может их исключить — на отборе (Шаг 2.5) они входят в список безусловно по флагу `marker: true`. Единственная точка, где маркерный кадр всё же может выпасть, — деградация по весу на Шаге 5 (крайний случай, с громким предупреждением).

Скрипт пишет `frames_work/candidates.json` — список `{cand_id, timecode, segment_id, marker, phrase}` по всем кандидатам (`marker`/`phrase` заполнены только у маркерных кадров; у остальных `marker=false`, `phrase=""`). Таймкоды нужны на Шаге 3 (relevant transcript excerpt по `cand_id`), `segment_id` — для детерминированной привязки кадр→сегмент на Шаге 4, `marker` — для гарантии на Шаге 2.5 и приоритета при обрезке веса на Шаге 5; иначе не восстановимы — сам CLI печатает только счётчик и путь к простыне.

*Примечание:* посегментный cap стартует с 10 кадров/сегмент, общий предохранитель — 150 (при переполнении cap ужимается для всех бакетов сразу; маркерные кадры в это ужатие не входят); `min_gap` — дефолт `dedup_by_gap` (3.0 с).

### Шаг 2. Триаж по простыне (Codex → фолбэк Sonnet)

По простыне **оценить каждого** кандидата (`{cand_id, type, confidence}`), включая заведомо шумные — читать текст не нужно, только классифицировать (говорящая голова/декор/дубль → `type=drop`). Триаж **не режет сам** — отбор shortlist вынесен в отдельный детерминированный под-шаг ниже.

В тот же вызов (без нового прохода по видео) подкладывается **выжимка ключевых мыслей конспекта по сегментам** — 1–2 строки на сегмент, что в нём главное. С этой выжимкой триаж дополнительно помечает по каждому кандидату: похож ли кадр на пустой/декоративный слайд («Пару слов, кто я», «Бонусы» — фотогеничный, но без сути) и бьётся ли он с мыслью конспекта своего сегмента. Это суждение, не жёсткий фильтр — окончательное решение по кадру всё равно принимает Ярус 2 (Шаг 2.5).

Если `codex_available()` (проверка `codex --version`) — идти через Codex (промпт первым, `-i` последним — вариативный флаг иначе съедает промпт):

```bash
codex exec --skip-git-repo-check --output-schema .claude/skills/konspekt/frames_schema.json \
  "Простыня пронумерованных кадров. Верни JSON: для КАЖДОГО кандидата поле type (prompt|slide-text|illustration|drop) и confidence. drop — говорящая голова/декор/дубль. Дополнительно, опираясь на выжимку конспекта по сегментам ниже, отметь пустые/декоративные кадры и бьётся ли кадр с ключевой мыслью своего сегмента. Читать текст не нужно, только отбор. Выжимка конспекта по сегментам: <segment_id → 1–2 строки ключевой мысли>." \
  -i "<work_dir>/contact_sheet.png"
```

Если `codex_available()` == false — тот же контракт (включая выжимку конспекта в промпте) через субагент актуального Sonnet (модель-алиас `sonnet`, не пин версии): Read по `contact_sheet.png`, вернуть тот же JSON по `frames_schema.json`.

### Шаг 2.5. Три яруса: план сегментов → посегментный отбор

Одноуровневый отбор заменён на три яруса (единица работы — сегмент, естественно совпадающая со структурой конспекта; про модели см. таблицу «Оркестрация и модели» ниже).

**Ярус 1 — разметка структуры (главный поток, только текст, без картинок).** По конспекту размечает каждому сегменту тип блока и политику плотности — это суждение оркестратора, а не жёсткая таблица. Ориентиры (список открытый, если сегмент не подходит ни под один — судить по смыслу):

| Ориентир (тип блока) | Что происходит | Политика скрининга |
|---|---|---|
| Контентный (плотная подача) | много объяснений и слайдов с полезной инфой | высокая частота — ловить все смысловые слайды |
| Демонстрация экрана | автор работает в инструменте вживую | низкая — 1–2 кадра на ключевых действиях, детально не нарезать |
| Маркетинговый (продажа продукта) | продаёт оффер | точечно — только ключевые слайды программы/оффера |
| Орг / вопросы-ответы | нет слайдов и демо | минимум — 1 кадр говорящей головы |

Результат сохраняется в `frames_work/segment_plan.json` — список объектов на сегмент:

```json
[{ "segment_id": "02", "block_type": "маркетинговый",
   "density": "точечно", "budget_hint": 2,
   "rationale": "продающий блок: только ключевые слайды оффера" }]
```

`block_type`/`density` — свободные ярлыки-суждения (не enum), `budget_hint` — ориентировочное число кадров-картинок сегмента, `rationale` — короткое обоснование, идёт в отчёт Шага 6.

**Ярус 2 — посегментный отбор + распознавание (≤3 субагента, Codex → фолбэк Sonnet).** Сегменты группируются в пачки функцией `batch_segments` — подряд идущие `segment_id` делятся на не более 3 смежных по времени пачек с балансировкой числа сегментов; при ≤3 сегментах — по одному на субагента, для совсем маленького видео (1–2 сегмента) можно обойтись одним вызовом без веера. Каждый субагент получает: свои записи `segment_plan.json`, срез `candidates.json` и результатов триажа по своим сегментам, посегментные `contact_sheet_seg<NN>.png`, срез транскрипта своих сегментов (`segment_transcript`), список промптов конспекта, попадающих в его сегменты. Возвращает per-cand решения: `{cand_id, segment_id, action: illustration|pr-block|drop, text?, caption, confidence}`.

Жёсткие правила Яруса 2 — не подлежат суждению, независимо от типа/плотности сегмента:
- кадр с `marker: true` в `candidates.json` — в отбор входит всегда;
- кадр с промптом на экране — всегда `action: pr-block`, текст распознаётся дословно со структурой (см. Шаг 3).

Если триаж (Шаг 2) пометил кадр «не бьётся с мыслью», а сегмент помечен высокоплотным — субагент вправе всё равно взять кадр, если видит ценность: последнее слово по конкретному кадру — за Ярусом 2.

**Детерминированная страховка покрытия (`select`).** `select_frames`/`adaptive_cap` из прежней механики никуда не делись, но их роль сузилась: они больше не главный отбор, а мягкая страховка на случай, если Ярус 2 что-то пропустил, — гарантия ≥1 кадра на сегмент, где вообще был non-drop кандидат, и верхняя sanity-граница на суммарное число немаркерных картинок. Результаты триажа Яруса 2 сводятся в один `frames_work/triage.json` (JSON по `cand_id`) — это вход `--triage`:

```
PYTHONUTF8=1 python "$HOME/.claude/skills/konspekt/frames_extract.py" select \
  --candidates "<рабочая-папка>/frames_work/candidates.json" \
  --triage "<рабочая-папка>/frames_work/triage.json" \
  --master-md "<рабочая-папка>/MASTER_[Название].md" \
  --segment-plan "<рабочая-папка>/frames_work/segment_plan.json" \
  --out "<рабочая-папка>/frames_work/shortlist.json"
```

`--segment-plan` — новый необязательный флаг: подкладывает `block_type` в печатаемый отчёт по сегментам (колонка «Тип блока», см. Шаг 6), на сам отбор не влияет. Внутри `select_frames` маркерные кадры (`marker: true`) входят вне cap и вне drop-фильтра триажа (гарантия из Шага 1); остаток адаптивного потолка `max(12, сегментов+10)` заполняется немаркерными кандидатами по убыванию `confidence`. Это **не** численный жёсткий предел — жёсткий ограничитель числа картинок в итоге задаёт вес виджета ≤8 МБ (`trim_to_weight`, Шаг 5). `shortlist.json` — вход и подстраховка для Шага 3/4 наряду с решениями Яруса 2.

### Шаг 3. Full-res разбор промптов и слайдов (Ярус 2: Codex → фолбэк Sonnet)

Выполняют субагенты Яруса 2 (Шаг 2.5) как часть своего посегментного вызова — отдельного прохода по видео или простыне не требуется.

**ЗАПРЕЩЕНО:** главный поток не вызывает `Read` по файлам `frames_work/**/*.png` или `SEC_кадры/**/*.png` — ни для «быстрой проверки», ни если Codex подвисает/недоступен. Единственные легитимные пути разбора кадра — `codex exec` ниже или Task-субагент (`sonnet`, см. фолбэк). Если оба недоступны — кадр помечается `type=drop`, а не разбирается вручную главным потоком.

Кандидаты своего сегмента (из среза `candidates.json`, включая маркерные и отобранные Ярусом 2 по ценности) — извлечь в полном разрешении и разобрать вместе с релевантным транскриптом (промпт снова первым, все `-i` — в конце). **Цель для промпт-кадров — распознать текст дословно, сохранив всю структуру** (переносы строк, отступы, нумерацию — то, что делает промпт копируемым как есть):

```bash
codex exec --skip-git-repo-check --output-schema .claude/skills/konspekt/frames_schema.json \
  "Для каждого приложенного кадра верни JSON-объект: type, дословный text (для prompt/slide-text — сохраняя переносы строк, отступы и нумерацию как на экране), caption, confidence. Если дословность промпта под сомнением — type=illustration, в caption пометь 'проверить'. Транскрипт: <вставить релевантные реплики с таймкодами>." \
  -i "<work_dir>/cand_0007.png" -i "<work_dir>/cand_0012.png"
```

**Политика уверенности:** при сомнении в дословности промпта/текста → не текстовый блок, а `type=illustration` + пометка «проверить» в `caption` — не выдавать искажённый копируемый текст как точный. Картинка-скриншот промпта — только запасной вариант на случай такого сомнения; источник истины для промпта всегда экран, не формулировка из конспекта.

Фолбэк — тот же контракт через субагент **актуального Sonnet** (алиас `sonnet`): если `codex_available()` == false, ИЛИ Codex вернул низкую `confidence` на конкретном кадре — точечно пересчитать этот кадр Sonnet-субагентом (Read по PNG → тот же JSON). Картинки в главный поток не возвращаются — только JSON по контракту `frames_schema.json` (`cand_id`, `timecode`, `type`, `text`, `caption`, `confidence`).

### Шаг 4. Вписать кадры в производную копию MD

Этому шагу PNG не нужны вообще — только per-cand решения Яруса 2 (`action`, `text`, `caption`) плюс `shortlist.json`/`candidates.json` как страховка покрытия. Главный поток (Ярус 3) работает исключительно с этим JSON и текстом мастер-MD; читать сами файлы кадров здесь незачем.

Оригинал `MASTER_[Название].md` не редактируется. Кадры вписываются в копию `MASTER_[Название]_с_кадрами.md` по решению `action`:

- **`pr-block`** (промпт на экране) → существующий блок промпта (`.pr-block`, см. «Блок промпта» выше) распознанным дословным текстом — новых конструкций не требуется;
- **`illustration`** (смысловой слайд, маркер-слайд, инфографика) → строка в `### Текст`: `![Подпись · таймкод](frames_work/cand_NN.png)` — подпись несёт таймкод и provenance для проверки и пересборки;
- **`drop`** (пустой/декоративный слайд, дубль, говорящая голова) — не вставляется;
- в сегментах-демонстрациях — не более 1–2 кадров на ключевых действиях (регистрация, открытие нового инструмента и т.п.), детально экран не нарезается;
- принадлежность сегменту берётся из `candidates.json` по `cand_id` (детерминированный join, посчитан на этапе `extract` по таймкоду события — у сегментов мастер-MD **есть** таймкоды в шапке `## Сегмент N | HH:MM:SS-HH:MM:SS | ...`).

Жёсткого посегментного потолка вставки нет — сколько кадров получит сегмент, решает Ярус 2 в рамках плотности из `segment_plan.json` (Шаг 2.5); `shortlist.json`/`adaptive_cap` — только sanity-страховка, не численный предел. Численного предела на вставку в принципе нет — единственный жёсткий предел итога — вес виджета ≤8 МБ (Шаг 5).

**ЗАПРЕЩЕНО:** после вставки не выводить содержимое `MASTER_[Название]_с_кадрами.md` (целиком или крупными фрагментами) в чат — это раздувает контекст без пользы. Итог сообщается сводкой (см. Шаг 6); полный текст файла — только если пользователь сам явно попросит его показать.

### Шаг 5. Сборка с контролем веса

```
PYTHONUTF8=1 python "$HOME/.claude/skills/konspekt/widget_generator.py" \
  "<рабочая-папка>/MASTER_[Название]_с_кадрами.md" \
  --shortlist "<рабочая-папка>/frames_work/shortlist.json"
```

Тот же генератор, что в Шаге 1 выше; умеет распознать строку-картинку в `### Текст`, ресайзить/сжать и base64-встроить как `<figure><img>…<figcaption>`. Выход — `WIDGET_[Название]_с_кадрами.html` (суффикс сохраняется в имени виджета — иначе сборка с кадрами перезапишет обычный `WIDGET_[Название].html` той же лекции). Инвариант `✅ JS syntax OK` сохраняется.

Флаг `--shortlist` включает контроль веса (`control_weight`): процедуру разрешения «покрытие vs вес ≤8 МБ» генератор выполняет **автоматически**. **8 МБ — жёсткий предел** (не ориентир). (1) картинки уже сжаты при рендере (ресайз 1280 / WebP q82 — даёт ~30 % веса даром против JPEG); (2) если итоговый HTML всё равно >8 МБ — `trim_to_weight` выбрасывает `<figure>` строго по приоритету `budget → mandatory → marker` (внутри группы — по возрастанию `confidence`): сначала кадры фазы бюджета, затем обязательные, и лишь в последнюю очередь — маркерные кадры «заскриньте»; (3) каждый выброшенный обязательный **и** маркерный кадр даёт `segment_id` в stderr (эти сегменты идут в отчёт Шага 6). Деградация маркерного кадра — крайний случай: печатается **громкое** предупреждение в stderr (спикер явно просил сохранить этот кадр, а вес его вытеснил). Тихого падения нет. Динамическое пере-сжатие (снижать качество перед выбрасыванием) — отложенное улучшение.

### Шаг 6. Отчёт и деградация

В конце ветки — сводка: кандидатов найдено / в shortlist / вставлено текстом / вставлено картинкой / отброшено, плюс таблица по сегментам (её печатает подкоманда `select` Шага 2.5). Колонка «Тип блока» берётся из `segment_plan.json` (Ярус 1) при переданном `--segment-plan`; иначе пустая:

```
Сегмент | Тип блока     | Кандидатов | Прошло триаж | Вставлено
01      | контентный    | 4          | 2            | 1
02      | маркетинговый | 0          | 0            | 0
```

Мягкая деградация — при любом сбое ветка не должна ронять весь виджет:

- видео недоступно (приватное/гео/устаревшие cookies) или yt-dlp упал → предупреждение, собрать обычный виджет без кадров;
- ffmpeg отсутствует → явная ошибка с инструкцией;
- кадр с нечитаемым текстом → в иллюстрацию или drop;
- битый/отсутствующий PNG при base64 → пропустить с предупреждением, продолжить сборку.

| Качество видео | 720p |
| Вес итогового HTML | **≤8 МБ — жёсткий предел** (единственный численный ограничитель числа картинок) |

## Оркестрация и модели

Ветка кадров дорогая по токенам из-за изображений — весь vision-объём (триаж + распознавание) выносится из главного Опус-потока: исполнитель «варит» картинки у себя и возвращает компактный JSON, не раздувая контекст мегабайтами PNG. Оркестрация — три яруса: Opus управляет (Ярус 1 — план, Ярус 3 — вставка/сборка), а весь vision отдан ≤3 субагентам Codex→Sonnet (Ярус 2).

| Ярус / шаг | Исполнитель | Модель | Почему |
|---|---|---|---|
| Подготовка: видео (yt-dlp) | Python | — | нет модели |
| Подготовка: scene-detection | Python (ffmpeg) | — | нет модели |
| Подготовка: маркеры + transcript-cues | Python regex | — (или Haiku) | узкий греп маркеров-гарантия + мягкие cue; дёшево |
| Подготовка: contact-sheets (общая + посегментные) | Python (ffmpeg tile) | — | нет модели |
| **Ярус 1 — план сегментов** | Главный агент (текст, без картинок) | Opus (актуальный) | размечает тип блока/плотность по конспекту → `segment_plan.json` |
| **Ярус 2 — триаж + отбор + распознавание** | ≤3 субагента по пачкам `batch_segments`, Codex → (фолбэк) Sonnet | Codex → Sonnet (актуальный) + политика уверенности | весь vision-объём вне Опус-бюджета; per-cand решения по своим сегментам, дословный разбор промптов |
| Страховка покрытия (`select`) | Python | — | мягкая гарантия ≥1 кадра/сегмент + маркеры вне cap; не главный отбор |
| **Ярус 3 — вставка + сборка** | Главный агент → Python | Opus (актуальный) | привязка кадр→сегмент и связность качество-критичны; сборка без модели |
| Реализация + код-ревью | Codex | — | силён в коде |

Модели в таблице — движки/алиасы, не пин версии: Codex подключается через доступность CLI (`codex_available()`), Sonnet — через алиас `sonnet`. При обновлении моделей таблица правки не требует.
