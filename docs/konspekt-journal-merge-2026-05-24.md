# Слияние журнала проекта: один индекс + файлы сессий

**Зафиксировано:** 2026-05-24. **Статус:** идея, реализация отложена.

## Проблема

Журнал ведётся в двух файлах, которые дублируются по содержанию:

- `docs/history.md` (~87 КБ, 771 строк) — в репозитории konspekt-project.
- `vibecoding vault/projects/konspekt-project.md` (~93 КБ, 455 строк длинных) — в хранилище.

Обе версии — построчный лог сессий проекта /konspekt, расхождения только в формулировках. Каждый раз при команде «обнови хранилище» агенту приходится Read'ить файл (truncated на >25K токенов, листать страницами) + Edit. Один цикл обновления — **~40–80K токенов**.

Если ввести правило «автообновлять history.md при обновлении хранилища» (висит после оборванной сессии 2026-05-23 из-за API-ошибки `invalid high surrogate`) — удвоится до **~80–160K за одно «обнови хранилище»**.

## Решение

Слить в одну архитектуру «индекс + файлы эволюции скилла».

Важное уточнение (2026-05-24): фиксируем **только эволюцию скилла** (архитектурные изменения, новые правила, переосмысления). Применения скилла (обработанные лекции, патчи, виджеты) — продукты, в журнал не идут. Это сразу режет ~70% содержимого текущих файлов.

- **`docs/evolution/INDEX.md`** — тонкий поисковый индекс: одна строка на событие эволюции (дата · короткое имя · одна фраза «что изменилось» · ссылка на файл). Загружается дешёво, всегда читается целиком.
- **`docs/evolution/YYYY-MM-DD-{slug}.md`** — отдельный файл на каждое архитектурное изменение.
- **Vault-файл (`vibecoding vault/projects/konspekt-project.md`)** — остаётся как «единое окно на проект» для не-журнальных разделов (Статус, Сделано, Решения, Обработанные материалы, Следующий шаг). Раздел сессий = ссылка на `docs/evolution/INDEX.md`.

«Обнови хранилище» становится: если в сессии была эволюция скилла — создать файл в `docs/evolution/` + строку в INDEX; обновить «Следующий шаг» и «Обработанные материалы» в vault-файле. Если эволюции не было — только vault. Каждое действие точечное, никаких Read 90KB.

## Вопросы на проработку перед реализацией

1. **Граница vault ↔ repo.** Файлы эволюции лежат в репо (`docs/evolution/`) — пользователь видит их в git. Vault-файл при этом остаётся в `vibecoding vault/` вне репо. Это нормальное разделение или эволюцию тоже хранить в vault?
2. **Миграция накопленного.** Из 16+ сессий в vault-файле вычленить только те, где была эволюция скилла (правки SKILL.md / новые правила / переосмысления архитектуры), и перенести в `docs/evolution/`. Применения скилла (обработка лекций) — отбрасываем. Если резать — сравнить с `docs/history.md` и взять более полную версию каждого события.
3. **Что делать с расхождениями между двумя текущими файлами.** Где-то формулировки одинаковые, где-то — нет. Какая версия — каноническая?
4. **Формат имени файла эволюции.** `2026-05-24-profiles-and-layer-merge.md` (короткий слаг по сути изменения).
5. **Формат строки индекса.** Минимум: `- 2026-05-24 — Активация профилей + слияние Слой 2+3 → [файл](2026-05-24-profiles-and-layer-merge.md)`. Достаточно или добавить теги/категории?
6. **Совместимость с CLAUDE.md.** Правило «при «обнови хранилище» — если была эволюция, создаём файл в `docs/evolution/` + строку в INDEX; в любом случае правим vault» нужно записать в `CLAUDE.md` проекта (это и было то самое поручение из оборванной сессии 2026-05-23).
7. **Раздел «Обработанные материалы» в vault.** Сейчас это таблица всех лекций — растёт линейно. Оставить как есть или тоже переосмыслить (например, отдельный файл `transcripts/processed.md` или метаданные внутри каждого мастер-MD)?

## Где менять при реализации

- Создать `docs/evolution/` + `INDEX.md` (первая запись уже есть — `2026-05-24-profiles-and-layer-merge.md`).
- Мигрировать накопленное (если решено) — пройтись по `vault/konspekt-project.md` и `docs/history.md`, выделить только события эволюции скилла, переписать в `docs/evolution/`.
- `vibecoding vault/projects/konspekt-project.md` — заменить раздел сессий на ссылку на индекс, остальные разделы (Статус, Сделано, Решения, Обработанные материалы, Следующий шаг) сохранить.
- `docs/history.md` — удалить после миграции.
- `CLAUDE.md` проекта — записать новый протокол «обнови хранилище».

## Ожидаемый эффект

Одно обновление журнала **~5–10K токенов вместо ~40–80K**. На длинной серии (5–10 сессий в неделю) — экономия **~150–700K токенов в неделю**.
