# 2026-07-11 — Ветка кадров: детерминированная привязка кадр→сегмент, pHash-дедуп, посегментные квоты, двухфазный отбор с гарантией покрытия

## Что изменилось

Opt-in ветка «виджет с кадрами» переведена с шумной **позиционной** детекции/вставки кадров на **детерминированную привязку кадр→сегмент по таймкоду** с гарантией покрытия. Реализовано по TDD-плану [docs/superpowers/plans/2026-07-07-konspekt-widget-frames-coverage.md](../superpowers/plans/2026-07-07-konspekt-widget-frames-coverage.md) (спека [docs/superpowers/specs/2026-07-07-konspekt-widget-frames-coverage-design.md](../superpowers/specs/2026-07-07-konspekt-widget-frames-coverage-design.md)). Ключевые новые части — все чистые тестируемые функции в `frames_extract.py`:

1. **Границы сегментов и привязка** (Фаза 1): `segment_bounds` — независимый парсер заголовков `## Сегмент N | HH:MM:SS-HH:MM:SS | Тема` из мастер-MD (числовые секунды, валидация непустоты/монотонности/непересечения) + `assign_segment` (таймкод → id сегмента: края, внутренний диапазон, щель → ближайшая граница).
2. **pHash-дедуп катов камеры** (Фаза 2): `average_hash` (average-hash 8×8 на PIL) + `hamming` + `phash_dedup` со скользящим окном N=3 — гасит повторные каты (в т.ч. циклические A→B→A).
3. **Посегментные квоты** (Фаза 3): `bucket_timecodes` — бакетирование scene+cue-таймкодов по сегментам, `dedup_by_gap` внутри каждого бакета с посегментным cap (старт 10) и общим предохранителем ~150 (единый нисходящий cap при переполнении). Переписан `build_candidates` (сигнатура на `master_md_text`, возврат `segment_id` + итоговый cap); CLI разбит на подкоманды `extract`/`select`, в манифесте `candidates.json` появился `segment_id`.
4. **Двухфазный отбор с гарантией + лимиты** (Фаза 4): `adaptive_cap = max(12, сегментов+10)`; `select_frames` — **обязательная фаза** (лучший non-drop кадр на каждый сегмент, где он был) + **фаза бюджета** (остаток по убыванию confidence по всему виджету); `trim_to_weight` (бюджет по возрастанию conf, затем деградация обязательных); `segment_report` (таблица кандидаты/прошло-триаж/вставлено) + подкоманда `select`. **Замкнута петля веса ≤8 МБ** (Task 4.4): `md_parser` эмитит `data-cand="NN"` на `<figure>`, `frame_weights` считает вес base64, `widget_generator.control_weight` меряет итоговый HTML и вырезает проигравшие `<figure>` через `trim_to_weight` — включается флагом `--shortlist`.
5. **Схема без `segment_hint`** (Фаза 5): из `frames_schema.json` убрано поле-догадка `segment_hint`; принадлежность сегменту восстанавливается детерминированным join по `cand_id`, а не угадыванием vision-моделью.
6. **Документация ветки** (Фаза 6): `layer2_widget.md` переписан — подкоманда `extract` + `--master-md`, новый Шаг 2.5 «Отбор shortlist» (детерминированный `select`), триаж скорит всех (не режет сам), full-res разбирает только shortlist, join по `cand_id`, автоконтроль веса, таблица по сегментам, обновлены «Лимиты по умолчанию» и таблица оркестрации.

## Почему так

Прошлая реализация ветки (2026-07-03) детектила и вставляла кадры **позиционно**, без опоры на структуру мастер-MD. Отсюда две системные боли: (а) шумные каты камеры (говорящая голова с разных ракурсов) плодили дубли; (б) не было гарантии, что каждый содержательный сегмент получит хотя бы один кадр, а богатый сегмент — больше одного, — отбор мог перекоситься.

Решение — сделать **границы сегментов первичным контрактом**: у сегментов мастер-MD **есть** таймкоды в шапке (частая ошибка прошлой прозы — «у сегментов нет таймкодов»), значит каждый кадр детерминированно привязывается к сегменту по таймкоду события, а не по догадке `segment_hint`. Дальше квоты/дедуп/отбор работают уже посегментно. Двухфазность (сначала гарантия ≥1, потом бюджет) отделяет **покрытие** от **богатства** и делает поведение предсказуемым. Петля веса замкнута отдельной задачей, потому что при адаптивном потолке 15–25 картинок `trim_to_weight` без замера итогового HTML был бы функцией без триггера (находка ревью плана — К2).

Развилки, принятые как компромисс метода (зафиксированы в плане): «пропорционально» реализовано как единый нисходящий cap для всех бакетов; overhead веса считается приближённо (итог минус вес картинок); «сначала сильнее сжать, потом резать» в MVP — фиксированное сжатие 1280/q82 + обрезка, динамическое пере-сжатие отложено. Известный риск: pHash-окно скользит через границы бакетов (raw отсортирован по таймкоду) — может изредка погасить первый кадр сегмента, похожий на хвост предыдущего; проверяется глазами на E2E, запасной вариант — дедуп внутри бакета.
