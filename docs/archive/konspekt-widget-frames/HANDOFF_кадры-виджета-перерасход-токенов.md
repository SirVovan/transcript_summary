# Хендофф: перерасход токенов в ветке «виджет с кадрами» — 2 сессии подряд съели весь 5-часовой лимит

Дата: 2026-07-07 · Проект: konspekt-project · Ветка: `feat/konspekt-widget-frames`

## Цель
Ветка «виджет с кадрами» реализована и в целом работает (см. [HANDOFF_кадры-виджета-реализация.md](HANDOFF_кадры-виджета-реализация.md) и `backlog.md`, коммиты по E2E-прогону). Но в двух реальных прогонах на рабочей машине (K_T_P) главный агент **читал скриншоты кадров напрямую в свой контекст** — вопреки контракту скилла — и это съело почти весь 5-часовой лимит Claude за одну сессию. Нужно закрыть эту лазейку в самом скилле/пайплайне, не полагаясь на прозу инструкции.

## Сделано (эта сессия — только диагностика, в другом проекте K_T_P)
Проанализированы два реальных лога сессий `/konspekt` (JSONL из `~/.claude/projects/...K-T-P/`):

1. **«Ледовских, 2 части» (2026-07-06, файл `2da06514-8558-4cb7-beb0-d03ef1c97223.jsonl`)** — целевая сессия.
2. **«Курилов, день 3» (тот же день, файл `db0803f2-06f8-4283-9aa0-32bb95d7afea.jsonl`)** — проверена для сравнения, паттерн совпал.

### Находка 1 — картинки читаются напрямую в главный поток (в обеих сессиях)
- Ледовских: 5 файлов `SEC_кадры\ч1_00-32-17.png` … `ч1_00-37-06.png` (~1.2 МБ каждый) прочитаны инструментом `Read` в главном потоке — **80% байтового объёма сессии** (6.1 из 7.6 МБ).
- Курилов: 23 файла `cand_NNNN.png` прочитаны так же — **81% байтового объёма** (16.8 из 20.7 МБ).
- По контракту скилла (`layer2_widget.md:214`) — «Картинки в главный поток не возвращаются — только JSON по контракту `frames_schema.json`». Т.е. документация уже запрещает это прямым текстом. Нарушение — не пробел в доке, а **исполнительское отклонение**: агент прочитал файлы напрямую (похоже, на шаге вставки/финальной сверки, уже после того как JSON от Codex/Sonnet был получен).
- В сессии Ледовских виден и полу-случившийся Codex-путь: `codex exec` с ad-hoc ТЗ (`codex_frames_spec.md`) запускался, но в момент проверки ещё не отдал результат (0 PNG в папке на тот момент) — похоже, когда кадры появились, сверку/вставку доделал сам главный агент, прочитав PNG напрямую, а не через Sonnet-фолбэк.
- В сессии Курилова Codex использовался **только** для грубого триажа по `contact_sheet.png` (Шаг 2) — детальный full-res разбор (Шаг 3, `layer2_widget.md:202-214`) в Codex вообще не уходил, все 23 кадра agent прочитал сам.

### Находка 2 — вес модели: Opus, а не Sonnet (более весомый фактор)
- В сессии Ледовских из 126 вызовов главного потока **107 — на `claude-opus-4-8`**, 19 — на `claude-sonnet-5`.
- Пиковый контекст ~270K токенов (раздут теми же картинками). Суммарно за сессию: **~17.8M токенов cache-read + 2.7M cache-creation**, почти всё на Opus.
- По таблице модели (`layer2_widget.md:263-279`) Opus в ветке кадров закреплён только за Шагом 5 («Вставка в копию MD» — качество-критично, `layer2_widget.md:275`). Остальные шаги (1,2,3 — кандидаты/триаж/разбор) по спецификации должны идти через Codex/Sonnet, не через Opus главного потока. Не проверено — действительно ли 107 opus-вызовов относились только к Шагу 5, или Opus тянул на себе больше шагов, чем задумано; это первое, что стоит проверить в новой сессии.

## Ключевые решения (и почему)
- Фикс — на уровне скилла (`konspekt-project`), не разовая инструкция: паттерн повторился в **двух независимых** реальных сессиях подряд, оба раза одинаково — это системная дыра, не случайность одной сессии.
- Прозы «картинки не возвращаются в главный поток» (уже есть в доке) **недостаточно** — агент её не соблюдает под давлением задачи. Нужен guard понадёжнее прозы (см. «Следующий шаг»).

## Грабли / чего избегать
- Не путать «Codex не рисует растр» (верно, генерация) с «Codex не видит растр» (неверно — видит, `codex exec -i <img>` работает, см. [HANDOFF_кадры-виджета-реализация.md](HANDOFF_кадры-виджета-реализация.md) — это уже фиксировали раньше как заметку памяти).
- Не путать целевую master-MD генерацию (обычный режим, Opus — намеренное решение, см. реализационный хендофф, п. «Мастер-MD режим остаётся на Opus») с веткой кадров — там Opus предназначен только шагу 5, это разные решения по разным причинам.
- JSONL-логи сессий на Windows: строки заканчиваются `\r\n` — при выгрузке `tool_use_id` через `jq` в файл нужно `tr -d '\r'`, иначе последующий `grep` не находит совпадений (наступил на это при диагностике).
