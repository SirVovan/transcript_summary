## Принципы распределения

### Что у нас на руках

| Модель | API ID | Биллинг | Сила | Слабость |
|---|---|---|---|---|
| **Opus 4.8** | `claude-opus-4-8` | подписка Max | флагман Anthropic (релиз 2026-05-28); смысловые акценты, координация, спорные решения; **Adaptive thinking** (effort `high` по дефолту, можно `xhigh`/`max` для самых тонких задач) | дорогая на массовку ($5/$25 за 1M) |
| **Sonnet 4.6** | `claude-sonnet-4-6` | подписка Max | дешевле в ~1.7×, быстрее, тот же стек; extended thinking при необходимости | чуть слабее на тонкой смысловой работе ($3/$15 за 1M) |
| **Codex (gpt-5.5)** | через `codex exec` | подписка ChatGPT | независимая модель = независимое мнение; следует инструкции буквально | плохо в смысловых акцентах; читает лишние файлы; накладные расходы на cold start (~13K служебных токенов на запуск) |

**Alias в Claude Code:** `opus` → `claude-opus-4-8`, `sonnet` → `claude-sonnet-4-6`, `haiku` → `claude-haiku-4-5`. Дефолт для подписки Max — `opus`. Версионированные ID начиная с 4.6 уже pinned snapshots (не evergreen), datestamp-суффиксы не нужны.

**Альтернатива subagent-driven:** в Claude Code есть готовый alias `opusplan` — связка «Opus для плана, Sonnet для выполнения». Концептуально это упрощённая версия нашей схемы. Я не использую её, потому что распределение должно быть **по задачам**, а не по фазам — некоторые «исполнительные» задачи всё равно требуют Opus.

### Правило выбора модели для каждой задачи

1. **Оркестратор (планирует / решает спорное / делает финальный merge)** → **Opus 4.8** (новая сессия).
2. **Реализация по детальной TDD-спеке без архитектурных решений** → **Sonnet 4.6** (свежий subagent). 70-80% задач плана попадают сюда.
3. **Независимое ревью кода** → **Codex 5.5** (subagent через `codex exec`). По принципу «вторая пара глаз» — он не видел нашу логику и придерётся ко всему, что мы упустили.
4. **Массовая генерация однотипного кода по жёсткому шаблону** → может быть Codex, но в нашем плане таких задач **нет**. Каждая задача — отдельный модуль с собственной логикой.
5. **Опционально для самых критичных задач** (security + state-machine: 1.4 key_storage, 2.2 invites, 4.4 главный handler, 5.1 connect_flow) — поднимать `effort` Opus с `high` до `xhigh` или `max`. Стоит дополнительных thinking-токенов, но снижает риск архитектурной ошибки в местах, где её сложно отловить тестами.

### Что Codex точно **не** надо отдавать в нашем плане

- Любую задачу с архитектурным решением, где нужно понять «что задумано».
- Задачи, где промт-инжекшн-защита, security, или авторская логика (т.е. почти все наши задачи).
- Тексты пользователя в `messages.py` (тон голоса, ToV — это смысловые акценты, провалит).
- `preview_prompt.md` разделение — поведенческая инвариантность, риск регрессии.

### Что Codex отдавать стоит

- **Ревью** после каждой фазы — независимый взгляд на код. Это то, что мы уже делали по spec, продолжим по коду.
- **Параллельные точечные ревью** при merge-конфликтах между задачами.

### Прикидка экономии

Цены за 1M токенов на 2026-05-29:
- Opus 4.8: $5 input / $25 output
- Sonnet 4.6: $3 input / $15 output
- Соотношение Opus:Sonnet ≈ **1.67× по input, 1.67× по output** (раньше я говорил «3-5×» — это была устаревшая инфа).

Если бы всё было на Opus 4.8: ~30 задач × ~50K input + ~10K output ≈ $7.5 в API-стоимости (на подписке Max — пропорционально лимиту).

С распределением:
- Opus 4.8: 11 × 60K ≈ $2.75
- Sonnet 4.6: 19 × 60K ≈ $2.85
- **Итого ≈ $5.6** при сопоставимом качестве → **экономия ~25%** к «всё на Opus».
- Codex ревью: 8 × 30K, **бесплатно из ChatGPT-подписки**.

Экономия скромнее, чем я говорил раньше — потому что Opus 4.8 подешевел относительно линейки 4.1 ($15/$75). Но логика распределения остаётся: 25% экономии без потери качества + независимое ревью Codex поверх.

**В терминах подписки Max:** меньше шанс упереться в лимит за сессию реализации, особенно если Opus-задачи запускать с `effort=high` (дефолт) вместо `xhigh`/`max`.

### Шаг 3: Subagent-driven flow

Skill будет:
1. Спавнить свежий subagent на каждую задачу — **с моделью из execution-документа** (передавать через `model` параметр в Agent tool, см. ниже).
2. Между задачами оркестратор (Opus) ревьюит результат.
3. Для критичных задач (отмечены «Codex после») — после ревью спавнить отдельный Codex-проход через `codex exec`.

### Как спавнить subagent с нужной моделью

Используется параметр `model` инструмента `Agent`. Алиасы Claude Code:
- `opus` → `claude-opus-4-8` (флагман, дефолт для Max)
- `sonnet` → `claude-sonnet-4-6`
- `haiku` → `claude-haiku-4-5`

```python
# Sonnet (большинство задач плана):
Agent({"subagent_type": "general-purpose", "model": "sonnet", "description": "...", "prompt": "..."})

# Opus 4.8 (архитектурные / security / тексты):
Agent({"subagent_type": "general-purpose", "model": "opus", "description": "...", "prompt": "..."})
```

Если оркестратор запущен на Opus и не указать `model` — subagent унаследует Opus. Поэтому **обязательно указывать `model: "sonnet"` для всех задач, помеченных как Sonnet**, иначе экономии не будет.

## Чего НЕ делать в новой сессии

- Не запускать всё одним subagent'ом — теряем ревью между задачами, теряем контроль.
- Не отдавать Opus задачи, помеченные как Sonnet — пустая трата токенов подписки.
- Не отдавать Sonnet задачи, помеченные как Opus (3.1 messages.py, 4.4 главный handler, 5.3 /connect handlers и т.д.) — риск регрессии тона / архитектурных ошибок.
- Не пропускать Codex-ревью после критичных задач (помечены «Codex после») — это страховка от слепых пятен.
- Не коммитить subagent — это делает оркестратор после ревью. Subagent ТОЛЬКО пишет код + тесты, тесты прогоняет, отчитывается.
- Не пускать subagent с `bypassPermissions` — обычные права.

## Если что-то идёт не так

| Симптом | Действие |
|---|---|
| Sonnet-subagent не справляется с задачей, помеченной как Sonnet | Эскалация: повторить с Opus. Запомнить причину. |
| Codex-ревью находит критичную проблему | Эскалация: Opus-subagent чинит, затем Codex второй проход. |
| Тесты падают после реализации | Subagent правит сам. Если 2 итерации не помогают — оркестратор разбирается inline. |
| `codex exec` падает с ошибкой подписки | Проверить `codex login`, дальше — пропустить ревью, чинить вручную. |
| Конфликт между задачами | Стоп. Inline разбирательство оркестратора. |
