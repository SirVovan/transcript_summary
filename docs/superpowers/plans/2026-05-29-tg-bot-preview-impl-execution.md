# План выполнения tg-бота — распределение задач по моделям

> Документ-компаньон к `2026-05-29-tg-bot-preview-impl.md`. Готовится к запуску в **новой сессии Claude Code**. Здесь — как распределить задачи между Opus 4.7 (текущая модель), Sonnet 4.6 и Codex 5.5 для оптимального соотношения «токены / качество / скорость».

**Дата:** 2026-05-29
**Контекст:** план содержит ~30 задач, 6 фаз, 13 раскрыто. Подход выполнения: **subagent-driven** (свежий subagent на каждую задачу + ревью между).

---

## Принципы распределения

### Что у нас на руках

| Модель | Биллинг | Сила | Слабость |
|---|---|---|---|
| **Opus 4.7** | подписка Max | смысловые акценты, координация, спорные решения | дорогая на массовку |
| **Sonnet 4.6** | подписка Max | дешевле, быстрее, тот же стек | чуть слабее на тонкой смысловой работе |
| **Codex (gpt-5.5)** | подписка ChatGPT | независимая модель = независимое мнение; следует инструкции буквально | плохо в смысловых акцентах; читает лишние файлы; накладные расходы на cold start (~13K служебных токенов на запуск) |

### Правило выбора модели для каждой задачи

1. **Орк­естратор (планирует / решает спорное / делает финальный merge)** → **Opus 4.7** (текущая сессия).
2. **Реализация по детальной TDD-спеке без архитектурных решений** → **Sonnet 4.6** (свежий subagent). 70-80% задач плана попадают сюда.
3. **Независимое ревью кода** → **Codex 5.5** (subagent через `codex exec`). По принципу «вторая пара глаз» — он не видел нашу логику и придерётся ко всему, что мы упустили.
4. **Массовая генерация однотипного кода по жёсткому шаблону** → может быть Codex, но в нашем плане таких задач **нет**. Каждая задача — отдельный модуль с собственной логикой.

### Что Codex точно **не** надо отдавать в нашем плане

- Любую задачу с архитектурным решением, где нужно понять «что задумано».
- Задачи, где промт-инжекшн-защита, security, или авторская логика (т.е. почти все наши задачи).
- Тексты пользователя в `messages.py` (тон голоса, ToV — это смысловые акценты, провалит).
- `preview_prompt.md` разделение — поведенческая инвариантность, риск регрессии.

### Что Codex отдавать стоит

- **Ревью** после каждой фазы — независимый взгляд на код. Это то, что мы уже делали по spec, продолжим по коду.
- **Параллельные точечные ревью** при merge-конфликтах между задачами.

### Прикидка экономии

Если бы всё было на Opus — ~30 задач × средняя задача ~50K токенов входа + ~10K выхода = **~1.8M токенов** Opus.

С распределением:
- Opus: 11 × 60K = ~660K Opus-токенов (то же качество, что и было)
- Sonnet: 19 × 60K = ~1.14M Sonnet-токенов
- Codex ревью: 8 × 30K = ~240K, **но не из подписки Anthropic** (отдельная)

**Sonnet ~3-5× дешевле Opus за токен в подписке Max.** Грубо: с распределением суммарная нагрузка на Anthropic-подписку **меньше в ~2 раза** при сопоставимом качестве. Codex — бесплатно сверху, лимит ChatGPT-подписки.

### Шаг 3: Subagent-driven flow

Skill будет:
1. Спавнить свежий subagent на каждую задачу — **с моделью из execution-документа** (передавать через `model` параметр в Agent tool, см. ниже).
2. Между задачами оркестратор (Opus) ревьюит результат.
3. Для критичных задач (отмечены «Codex после») — после ревью спавнить отдельный Codex-проход через `codex exec`.

### Как спавнить subagent с нужной моделью

Используется параметр `model` инструмента `Agent`:

```python
# Sonnet:
Agent({"subagent_type": "general-purpose", "model": "sonnet", "description": "...", "prompt": "..."})

# Opus (или просто опустить — он по умолчанию):
Agent({"subagent_type": "general-purpose", "model": "opus", "description": "...", "prompt": "..."})
```

Для Codex-ревью — Bash с `codex exec` (см. шаблон ниже).

## Чего НЕ делать в новой сессии

- Не запускать всё одним subagent'ом — теряем ревью между задачами, теряем контроль.
- Не отдавать Opus задачи, помеченные как Sonnet — пустая трата токенов подписки.
- Не отдавать Sonnet задачи, помеченные как Opus (3.1 messages.py, 4.4 главный handler, 5.3 /connect handlers и т.д.) — риск регрессии тона / архитектурных ошибок.
- Не пропускать Codex-ревью после критичных задач (помечены «Codex после») — это страховка от слепых пятен.
- Не коммитить subagent — это делает оркестратор после ревью. Subagent ТОЛЬКО пишет код + тесты, тесты прогоняет, отчитывается.
- Не пускать subagent с `bypassPermissions` — обычные права.

## Если что-то идёт не так

| Симптом | Действие |
|---|---|
| Sonnet-subagent не справляется с задачей, помеченной как Sonnet | Эскалация: повторить с Opus. Запомнить причину. |
| Codex-ревью находит критичную проблему | Эскалация: Opus-subagent чинит, затем Codex второй проход. |
| Тесты падают после реализации | Subagent правит сам. Если 2 итерации не помогают — оркестратор разбирается inline. |
| `codex exec` падает с ошибкой подписки | Проверить `codex login`, дальше — пропустить ревью, чинить вручную. |
| Конфликт между задачами | Стоп. Inline разбирательство оркестратора. |
