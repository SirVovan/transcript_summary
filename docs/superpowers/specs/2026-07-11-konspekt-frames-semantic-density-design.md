# Смысловая плотность кадров в ветке «виджет с кадрами» — Design

Дата: 2026-07-11 · Проект: `/konspekt` (скилл), ветка `feat/konspekt-widget-frames`
Статус: черновик на согласование

## Проблема

Механизм вставки кадров в виджет отбирает картинки **снизу вверх** и без опоры на смысл конспекта. ffmpeg находит смены картинки (scene-detect), таймкоды бакетируются по сегментам (равномерная квота), триаж классифицирует «слайд/голова/мусор», отбор берёт по визуальной уверенности. Конспект в цепочке участвует только как источник границ сегментов (таймкоды в шапке), но не как источник **ценности**.

Следствия, зафиксированные на реальном производстве (Ледовских, Практикум «Агент для контента», Д1 ч1 — `F:\Наш Архив\ИИ\Ледовских\Интенсивы\Практикум - Агент для контента\`):

1. Слайды, которые спикер прямым текстом просил заскринить (формула «350 = 100 000 ₽», блок «5 ошибок»), **не попали даже в кандидаты** — scene-detect их не выцепил, маркер «заскриньте» кадр на точной секунде не гарантировал.
2. Равномерный лимит (≤2, а затем адаптивный потолок из плана 2026-07-07) выбрасывал ценные слайды в слайд-плотных блоках.
3. Вставлялись пустые фотогеничные слайды («Пару слов, кто я», «Бонусы») — триаж видит «слайд с текстом», но не видит, что текст неважный.
4. Реальные промпты понижались до цитат вместо копируемых `.pr-block`.
5. Смысловые слайды без маркера и пропущенные scene-detect (напр. «Ошибка 3/4/5») терялись безвозвратно.

Корень один: **отбор не знает, что в конспекте считается ценным, и не учитывает неравномерную плотность полезного по ходу выступления.**

## Ключевой принцип решения

**Дополнить, не заменять.** Вся нынешняя механика (scene-detect → бакеты → дедуп → триаж → отбор → разбор → вставка → сборка с контролем веса) остаётся как дешёвый поставщик кандидатов. Сверху добавляются точки, где в неё вливается **смысл конспекта**, — все они либо суждение оркестратора над текстом конспекта, либо дешёвый греп транскрипта. **Ни одного нового прохода по видео не вводится.**

Смысл входит в трёх местах:

1. **Маркеры «заскриньте»** — греп транскрипта, кадр режется принудительно на точной секунде (без модели, почти даром).
2. **Плотность по сегменту** — оркестратор судит по простыне кандидатов + конспекту, сколько и каких кадров брать, по ценности блока (гибко, не по фиксированной таблице).
3. **Промпты** — находятся на экране, распознаются дословно с сохранением структуры, ложатся в `.pr-block` (vision только у промпт-кадров).

Full-res распознаётся **только у отобранных**. Плотность скрининга следует из структуры выступления, а не из равномерной квоты.

## Плотность как гибкое суждение (а не справочник типов)

Плотность полезной информации по видео неравномерна. Закрытый список типов блоков построить нельзя — их всегда больше, чем удаётся перечислить. Поэтому **тип блока и политику плотности определяет оркестратор** (главный Opus-поток, который и так читает конспект), опираясь на ориентиры-примеры, а не на детерминированную таблицу:

| Ориентир (тип блока) | Что происходит | Политика скрининга |
|---|---|---|
| Контентный (плотная подача) | много объяснений и слайдов с полезной инфой | высокая частота — ловить все смысловые слайды |
| Демонстрация экрана | автор работает в инструменте вживую | низкая — 1–2 кадра на *ключевых действиях* (регистрация, открытие нового инструмента), детально не нарезать |
| Маркетинговый (продажа продукта) | продаёт оффер | точечно — только ключевые слайды программы/оффера, тезисно |
| Орг / вопросы-ответы | нет слайдов и демо | минимум — 1 кадр говорящей головы |

Список **открытый**: если сегмент не лезет ни в одну корзину, оркестратор судит по смыслу. Ориентиры живут как guidance-текст в `layer2_widget.md`, а не как код.

Поверх плотности — два жёстких правила, независимо от типа блока:
- маркер «заскриньте» → кадр обязателен всегда;
- промпт из конспекта → всегда `.pr-block` распознанным текстом.

## Промпты: источник истины — экран

Раньше подразумевалось, что текст промпта можно взять из конспекта. Это неверно: **источник истины для промпта — сам экран.** Агент (субагент Яруса 2):
1. находит кадр, где промпт показан на экране;
2. распознаёт его **дословно, сохраняя всю структуру** (переносы строк, отступы, нумерацию — всё, что делает промпт копируемым как есть);
3. отдаёт распознанный текст в `.pr-block`.

Картинка-скриншот промпта — только запасной вариант, если распознать дословно не удалось (действующая «политика уверенности»: сомнение → `type=illustration` + пометка «проверить» в подписи).

## Оркестрация: три яруса

Сегмент — естественная единица работы, совпадающая со структурой конспекта (в предыдущей сессии это делалось руками — `step3_seg1..5.json`, `step3_markers.json`). Формализуем в три яруса:

| Ярус | Кто | Модель | Работа |
|---|---|---|---|
| 1. Разметка структуры | Главный поток | **Opus** (актуальный алиас) | по конспекту размечает каждому сегменту тип блока + политику плотности. Только текст, картинок нет. Требует вида на всё выступление — потому в главном потоке |
| 2. Посегментный отбор + распознавание | **≤3 субагента** (пачки сегментов) | **Codex → фолбэк Sonnet** | по ярлыку блока, кандидатам-миниатюрам своего сегмента, куску транскрипта и списку промптов: выбрать кадры по ценности, распознать промпты дословно со структурой → компактный JSON |
| 3. Сшивка + вес + сборка | Главный поток | **Opus** (актуальный алиас) | смёржить посегментные результаты, применить общий вес ≤8 МБ, собрать виджет |

Правила яруса 2:
- субагентов **не более трёх**; сегменты группируются в ≤3 пачки (при ≤3 сегментах — по сегменту на субагента, при большем числе — пачками);
- внутри субагента — Codex, если `codex_available()`; иначе субагент актуального Sonnet (алиас `sonnet`);
- Opus — только на управлении (Ярусы 1 и 3), в субагенты не опускается.

**Честная оговорка про стоимость.** Субагенты экономят контекст главного потока (миниатюры простыни и разборы кадров туда не текут) и время (пачки считаются параллельно), но **не суммарные токены**. Экономия по деньгам — за счёт Sonnet/Codex в Ярусе 2 вместо Opus. Качество-критичные части (глобальная разметка структуры, финальная сшивка/связность вставки) остаются на Opus.

## Изменения по шагам ветки

Пометки: ✎ — правка, `=` — без изменений. Нумерация шагов — как в `layer2_widget.md`.

- **Шаг 0. Вход** `=` — URL/локальный файл, мягкая деградация при отсутствии видео.
- **Шаг 1. Кандидаты** ✎ — маркер-греп становится **гарантированным** источником: на каждый «заскриньте/скриньте/зафиксируйте/поскринь» кадр режется на точной секунде в обход scene-detect; если маркер указывает на серию слайдов — берётся несколько кадров по короткому окну. В `candidates.json` у таких кадров флаг `marker: true` + фраза спикера. scene-detect, pHash-дедуп, посегментные бакеты — как есть.
- **Шаг 2. Триаж по простыне** ✎ — в тот же вызов (без нового прохода) подкладывается выжимка ключевых мыслей конспекта по сегментам; триаж дополнительно помечает «пустой/декоративный» и «бьётся ли с мыслью конспекта».
- **Шаг 2.5. Отбор** ✎✎ — главная правка. Вместо единого адаптивного потолка — **трёхъярусная схема** выше: Ярус 1 (Opus) размечает плотность по сегментам, Ярус 2 (≤3 субагента) отбирает кадры по ценности и распознаёт промпты. Жёсткие правила поверх: маркер-кадр обязателен; промпт → `.pr-block`. Детерминированный `select` из плана 2026-07-07 остаётся **страховкой покрытия и весом**, но единый потолок не диктует.
- **Шаг 3. Full-res разбор** ✎ — у промпт-кадров цель — распознать **дословно со структурой**; сомнение → картинка + «проверить». Слито с Ярусом 2 (субагенты).
- **Шаг 4. Вставка** ✎ — промпты → `.pr-block` распознанным текстом; смысловые/маркер-слайды → картинкой с подписью-таймкодом; демо → 1–2 кадра; пустые не вставляются. Жёсткого посегментного потолка нет — правит суждение Шага 2.5.
- **Шаг 5. Сборка с контролем веса** `=` — ≤8 МБ, `trim_to_weight`.
- **Шаг 6. Отчёт** ✎ — в таблицу по сегментам добавляется **тип блока**, к которому оркестратор отнёс сегмент, и краткое «почему столько кадров» (прозрачность решения).

## Границы: детерминированное ядро vs суждение

**Детерминированное (Python, покрывается тестами по TDD):**
- маркер-греп + гарантированная нарезка кадра на точной секунде + окно для серии слайдов;
- флаг `marker` и фраза спикера в `candidates.json`;
- нарезка транскрипта по сегментам (вход субагентам Яруса 2);
- группировка сегментов в ≤3 пачки;
- контроль веса ≤8 МБ и таблица отчёта (существует).

**Суждение (в `layer2_widget.md`, проверяется на E2E, не юнит-тестами):**
- разметка типа блока и политики плотности (Ярус 1);
- выбор кадров по ценности блока (Ярус 2);
- распознавание промптов дословно со структурой (Ярус 2).

## Осознанно отложено (не в этом дизайне)

- **Конспект-управляемый поиск вслепую** для слайдов, которые спикер не просил скринить *и* scene-detect пропустил (правая нижняя клетка матрицы «просил × заметил»). Начинаем без него; если E2E покажет заметные потери в этой клетке — достраиваем отдельно.
- **Динамическое пере-сжатие** кадров перед выбрасыванием по весу (уже отложено в плане 2026-07-07).
- Более трёх субагентов / рой по сегменту — сознательно ограничено тремя.
