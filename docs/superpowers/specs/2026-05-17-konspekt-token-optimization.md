# Оптимизация скилла /konspekt по расходу токенов

**Дата:** 2026-05-17
**Контекст:** аудит [docs/token-audit-2026-05-17.md](../../token-audit-2026-05-17.md) и handoff [docs/konspekt-optimization-handoff.md](../../konspekt-optimization-handoff.md)
**Цель:** уменьшить расход токенов с ~700K до ~250–300K на 1.5 часа лекции (экономия ~57–64%) без потери качества мастер-MD.

## Что именно меняем — обзор

## 1. Перенос читательской самопроверки Ф2 на бригадира

**Проблема.** Каждый из 6 субагентов Ф2 пишет блок «Самопроверка — глазами Аудитории» (2–3 абзаца рефлексии + перечень правок). В прошлом прогоне 6 из 6 субагентов вывели «менять ничего не нужно». Стоимость: ~18K output + ~6K input на инструкцию × 6.

**Решение.** Убрать читательскую самопроверку из `subagent_phase2.md` целиком. Бригадир делает **один читательский ревью по уже собранному мастер-MD** — это есть и сейчас в виде «Финальной самопроверки мастер-MD — глазами Аудитории», но фактически он перекрывает ту же задачу: проверить, понятен ли результат целевой Аудитории. Локальная оптика 6× субагентов заменяется одной целостной оптикой по всему выступлению (что объективно ближе к тому, как реальный читатель воспринимает текст).

**Что правим:**

- `subagent_phase2.md`: удалить разделы «Самопроверка — глазами Аудитории» (строки 14–16 в роли, 38, 187, 238–278, и упоминания в формате итогового ответа на строках 166–169, 184–189). Оставить только техническую самопроверку.
- `brigadir.md` раздел «Верификация текста»: удалить шаги проверки читательского блока субагента (строки 199–209). Технический блок субагента продолжаем проверять.
- `brigadir.md` раздел «Финальная самопроверка мастер-MD — глазами Аудитории»: усилить ориентиры — явно включить проверку «понятна ли логика автора целевой Аудитории, не запутается ли она в конкретных формулировках», чтобы покрыть зону ответственности, которая раньше лежала на субагентах.

**Эффект:** ~13K сэкономлено на прогон. Архитектурный бонус: читательская оптика становится цельной, а не местечковой.

## 2. Встраивание спек в промт + сокращение спек вдвое

**Проблема.** Каждый из 6 субагентов Ф2 через Read открывает `subagent_phase2.md` (~5K), `tov_spec.md` (~3K), `audience_spec.md` (~1K). Это ~9K × 6 = **~54K input на повторное чтение неизменного контента**. Плюс `subagent_phase2.md` (289 строк) и `tov_spec.md` (138 строк) содержат антисаботажные дубли и многословные пояснения — половина объёма не несёт уникальной нагрузки.

**Решение.**

- **Встраивание.** Бригадир читает три спек-файла **один раз** при подготовке к Ф2, передаёт их содержимое каждому из 6 субагентов как блоки `[INSTRUCTIONS]`, `[TOV]`, `[AUDIENCE]` внутри prompt'а Agent-вызова. Субагент **не** делает Read этих файлов.
- **Сокращение.** `subagent_phase2.md` и `tov_spec.md` сокращаются примерно вдвое:
  - Убрать дублирующиеся антисаботажные формулировки, оставив одну формулировку каждого правила.
  - Сжать примеры до одного на правило (не два-три).
  - Объединить разделы «Принципы сохранения авторского голоса» и «Полнота содержания» в один (сейчас они перекрываются по смыслу).

**Что правим:**

- `brigadir.md` раздел «Фаза 2: Написание текста»: бригадир выполняет один раз `Read` на `subagent_phase2.md`, `tov_spec.md`, `audience_spec.md`, и встраивает их содержимое в промт каждого Agent-вызова.
- `subagent_phase2.md` строки 36–38 (про чтение `audience_spec.md`): удалить.
- `subagent_phase2.md`: сократить до ~150 строк, убрав дубли и расширенные примеры. Сохранить ядро: роль, входы, процесс, обязательные блоки в выводе, критерии качества.
- `tov_spec.md`: сократить до ~70 строк, оставив только активные правила голоса.
- `SKILL.md` строка 122 («Прочитать `subagent_phase1.md` и передать его содержимое каждому субагенту в начале промпта») — этот паттерн расширить на Ф2: бригадир делает то же самое с `subagent_phase2.md` + `tov_spec.md` + `audience_spec.md`.

**Эффект:** ~50–70K input сэкономлено на прогон.

## 3. Sonnet для Ф1 и Ф2, Opus для бригадира

**Проблема.** Все субагенты сейчас наследуют модель Opus 4.7 от бригадира. Задача субагентов Ф2 — это **rewrite с сохранением голоса** (по чётким инструкциям), а не reasoning. Задача субагентов Ф1 — **сегментация по правилам** (тоже не reasoning). Sonnet 4.6 справляется с такими задачами сопоставимо с Opus, при разнице в стоимости ~×5.

**Решение.** Бригадир указывает `model: "sonnet"` явно в каждом Agent-вызове Ф1 и Ф2. Сам бригадир остаётся на Opus, потому что он делает сегментацию верхнего уровня, сборку мастер-MD, финальную самопроверку, гармонизацию — задачи, где Opus оправдан.

**Что правим:**

- `brigadir.md` раздел «Фаза 1: Черновая сегментация (параллельно)»: добавить указание «при вызове Agent для каждого чанка указать `model: "sonnet"`».
- `brigadir.md` раздел «Фаза 2: Написание текста (параллельно)»: то же самое для субагентов Ф2.
- `SKILL.md`: в обоих разделах про Ф1 и Ф2 добавить пометку «модель субагента — Sonnet».
- Никаких изменений в инструкциях самих субагентов (`subagent_phase1.md`, `subagent_phase2.md`): антисаботажные правила и работают именно для того, чтобы любая модель не срезала смысл.

**Эффект:** ~325K Opus-эквивалента сэкономлено (~47% от общего бюджета). Это самый крупный рычаг в спеке.

**Риски и митигация:**

- Sonnet может чуть строже следовать букве и хуже улавливать тонкие нюансы ToV → митигируется чётким `tov_spec.md` после сокращения.
- Sonnet может проседать по объёму к нижней границе 70% → митигируется явной проверкой объёма в технической самопроверке.
- Обязательно: тестовый прогон на эталоне (см. раздел «Тестирование»).

## 4. Гибридный ToV: файл серии + head-выборка

**Проблема.** Бригадир сейчас читает первый чанк целиком (~18K в контекст) ради извлечения ToV. Реально для этого нужны первые 2–3K токенов транскрипта.

**Решение.** Гибридная логика в бригадире:

1. Бригадир ищет файл `transcripts/tov_<серия>.md`. Имя серии берётся из имени транскрипта (например, «ПОЛНЫЙ курс Claude Code 2026» → `tov_full-claude-code-2026.md`).
2. Если файл есть — бригадир читает его (~1K) и использует как ToV.
3. Если нет — бригадир запускает `python preprocessor.py head <транскрипт>` (новая команда), получает первые ~2–3K токенов, извлекает ToV, сохраняет в `tov_<серия>.md` для следующих частей.

**Что правим:**

- `preprocessor.py`: добавить команду `head <транскрипт> [--tokens N]` (по умолчанию `N=2500`), возвращающую первые ~N токенов транскрипта без таймштамповой разметки чанков.
- `brigadir.md` раздел «Динамический ToV» (в `SKILL.md` строки 112–115): развернуть в полноценный раздел с гибридной логикой выше.
- `SKILL.md` строки 112–115: обновить ссылкой на новую логику в `brigadir.md`.

**Эффект:** ~15K на первом прогоне серии, ~17K на каждом следующем прогоне той же серии.

## 5. Дисциплина бригадира

**Проблема.** «Накладные расходы на контекст между ходами» бригадира — 60–100K (10–15% бюджета). Большая часть — структурный налог Claude Code и неустранима. Но часть срезается явными правилами.

**Решение.** В `SKILL.md` и `brigadir.md` добавить явные ограничения для бригадира:

1. **Не использовать TodoWrite** в /konspekt-пайплайне. Пайплайн линейный, прогресс виден из текстовых сообщений. Schema-reload TodoWrite (~5K) не оправдан.
2. **Не перечитывать чанки после Ф1.** После получения черновых карт от субагентов Ф1 чанки доступны только точечно (по таймштампу при разрешении сомнений в сегментации). Никаких полных Read чанка после Ф1.
3. **Не запускать дополнительные deferred tools** (Plan, и т.п.).

**Что правим:**

- `SKILL.md`: добавить раздел «Дисциплина бригадира» сразу после «Точки остановки», содержащий три правила выше.
- `brigadir.md` в начале «Роли»: подключить ссылку на дисциплину.

**Эффект:** ~15–25K на прогон.

## 6. Заморозка раздела «Траектория»

**Проблема.** Раздел «Траектория» (после «Логической реконструкции»): абзац прозой + таблица «Сегмент → Тайм → Ход → Описание» по таксономии из 8 ходов + своя самопроверка. Стоимость на прогон: ~1.5K output + ~1K input на инструкцию. В текущем виде раздел не даёт ценности, для которой задумывался — развивать его потребовало бы отдельных ресурсов.

**Решение.** Заморозить, не удаляя. Раздел остаётся видим в `brigadir.md` под HTML-комментарием `<!-- FROZEN: ... -->` или в отдельном файле `brigadir_frozen.md`. Пайплайн его не выполняет. Раскомментирование — одна правка, если в будущем будут ресурсы.

**Что правим:**

- `brigadir.md`: обернуть раздел «Траектория — методолог» (строки 338–391) и упоминание в «Сборке» в `<!-- FROZEN: ... -->`.
- `brigadir.md` раздел «Бригадир: Сборка» в `SKILL.md` (строка 172): убрать упоминание «Траектория — методолог (с самопроверкой)» из списка шагов.
- `brigadir.md` раздел «Сборка мастер-MD — редактор»: убрать раздел `## Траектория` из шаблона мастер-MD (не должен фигурировать на выходе).
- `brigadir.md` раздел «Очистка перед сохранением»: убрать `(траектория)` из списка вырезаемых самопроверок (раздела не будет вообще).

**Эффект:** ~2.5K. Главная ценность не в экономии, а в очищении пайплайна от неработающего блока.

## 7. Методичка сегментации: «уровень главы» + анти-маркеры + серийный контекст как эталон

**Проблема.** Бригадир склонен к размельчению сегментов. В диалоге [docs/Пример сегментации.md](../../Пример%20сегментации.md) на тех же ~1.5 часах он выдал 21 сегмент вместо нужных 6. Бригадир сам признал причину: «брал каждый маркер смены формата (новая фича, новая демо, новая команда) как границу сегмента, вместо того чтобы держать единицу масштаба "крупная мысль автора"». Текущая формулировка «сегмент = одна самостоятельная мысль» слишком пластична и допускает уровень «параграфа», а не «главы».

Самопроверка глазами Аудитории при этом не сработала — вывела «менять ничего не нужно», потому что не содержит ориентира «не слишком ли мелко».

Дополнительный фактор: у пользователя серийные транскрипты (курсы из нескольких частей). Часть 1 уже задаёт эталонный масштаб (8 сегментов на ~95 мин), но методичка не использует `[SERIAL CONTEXT]` как масштабный эталон.

**Решение.** Три согласованных правки в методичке + одна в самопроверке.

**Что правим в `subagent_phase1.md` (раздел «Правила сегментации»):**

- Добавить **целевой масштаб**: «Ориентир — 5–10 сегментов на 60–90 минут лекции, ~10–15 минут на сегмент. Это уровень "главы курса", не "параграфа". Если вышло заметно больше — почти всегда это размельчение.»
- Добавить **анти-маркеры** (что **не** является границей):
  - Смена формата внутри одной темы (теория → демо → ещё демо одной темы)
  - Новая фича / команда / лайфхак, раскрывающая ту же мысль
  - Метафора, пример, оговорка по основной мысли
- Уточнить формулировку «самостоятельная мысль»: «крупная тема, ради которой автор отвёл существенный кусок времени, со всеми её разворотами — концепт, демо, минусы, обход, ещё демо. Уровень главы курса, а не параграфа.»

**Что правим в `brigadir.md` (раздел «Глобальный обзор — методолог»):**

- Перенести те же три блока (целевой масштаб, анти-маркеры, уточнённое понятие «самостоятельной мысли»).
- Добавить **использование серийного контекста как масштабного эталона**: «Если есть мастер-MD предыдущей части (`[SERIAL CONTEXT]` показывает наличие), посмотри сколько сегментов было там при сопоставимой длительности и держи аналогичный масштаб. Это сильнейший ориентир.»
- Добавить **тест на укрупнение** перед выдачей чистовой карты: «Пройдись по соседним парам сегментов и спроси: если объединить эти два, получится одна развёрнутая мысль? Если да — объединить. Если нет — оставить.»

**Что правим в `brigadir.md` (раздел «Самопроверка — глазами Аудитории (сегментация)»):**

- Добавить в «На что обратить внимание» новый ориентир: «**Не слишком ли я дроблю?** Не дал ли я каждой новой команде, демо или лайфхаку отдельный сегмент вместо того, чтобы держать их как части одной крупной мысли? Если в карте >10 сегментов на 60–90 минут — это сигнал перечитать критически.»

**Эффект.** Прямая экономия — косвенная: меньше сегментов = меньше субагентов Ф2 = меньше output. Если за счёт правки число сегментов идёт с 12 к 7 — это уже минус 5 субагентов Ф2 = минус ~250K output на Opus или минус ~50K на Sonnet. С учётом #3 (Sonnet) — экономия ~50K на типичном прогоне, плюс снимается необходимость ручного укрупнения.

## 8. Параграфы как `####` подразделы внутри Текста

**Контекст.** При укрупнении сегментации (см. #7) теряется детализация в навигации. Решение: бывшие «параграфы» — те темы, которые раньше становились отдельными мелкими сегментами — теперь становятся **подзаголовками `####`** внутри Текста сегмента. Размер сегмента укрупняется, но детализация навигации сохраняется на уровень ниже.

**Решение.** Расширить правила оформления Текста в `subagent_phase2.md` и шаблон сборки в `brigadir.md`.

**Что правим в `subagent_phase2.md` (раздел «Что произвести / Текст / Правила оформления Текста»):**

- Добавить правило: «Для сегмента с несколькими подтемами (>1 подтемы из ключевых тезисов SEGMENT SPEC) использовать подзаголовки `####` для членения Текста на смысловые подразделы. Источник заголовков — ключевые тезисы из [SEGMENT SPEC] или естественные подтемы транскрипта.»
- Под каждым `####` — компактный блок 3–6 абзацев в той же манере, что весь Текст сейчас (первое лицо, жирное на ключевых терминах, голос спикера).
- Если в сегменте одна подтема — `####` не нужны, Текст пишется как сейчас.

**Что правим в `subagent_phase2.md` (раздел «Что произвести / Карта»):**

- Уточнить роль Карты: «Карта = **ключевые тезисы Текста** (что сказано/доказано), а не оглавление подразделов. Подзаголовки `####` в Тексте — отдельная сущность, отвечающая на вопрос «о чём раздел». Карта отвечает на вопрос «что сказано». Эти два списка не должны дублировать друг друга — если ты замечаешь, что Карта и подзаголовки звучат одинаково, перепиши Карту в форме тезисов-утверждений.»

**Что правим в `brigadir.md` (раздел «Сборка мастер-MD — редактор»):**

- В шаблоне сегмента под `### Текст` указать, что Текст может содержать подзаголовки `####`.

**Эффект.** Прямой экономии нет; это компенсация качества, без которой #7 был бы регрессом по навигации. Вместе #7 + #8 дают то же качество детализации, что 21 сегмент, но в формате 6 сегментов.

## Тестирование

**Эталон.** Транскрипт «ПОЛНЫЙ курс Claude Code 2026 ч2.txt» (1:32:59). Эталонный мастер-MD: `transcripts/ПОЛНЫЙ курс Claude Code 2026 ч2_мастер.md`.

**Процедура.**

1. Тестовый прогон **в отдельной сессии** (не той, где делались правки — это требование handoff-документа).
2. Сравнить новый мастер-MD с эталоном по:
   - Авторский голос сохранён (выборочно: 3 случайных абзаца)
   - Все ключевые тезисы из эталонной карты на месте
   - Объём близок к эталонному (±15%)
   - Сегментация даёт 5–8 сегментов (не 12+)
   - Внутри сегментов есть подзаголовки `####`, отражающие подтемы
3. Зафиксировать токенный расход прогона. Целевая отметка: ≤300K.

**Если качество просело** — откатить #3 (модели Sonnet) до F1 (Sonnet только для Ф2) или до F4 (всё на Opus), сохранить остальные правки.

## Порядок реализации

Все 8 пунктов независимы в реализации и могут идти в любом порядке внутри одной сессии. Тестовый прогон проводится **после применения всех правок**, в отдельной сессии. Если тестовый прогон выявит регресс — итеративный откат отдельных пунктов согласно матрице рисков (см. «Тестирование»).

Конкретный план шагов с порядком, командами и контрольными точками — отдельный документ, создаётся по этому спеку через writing-plans.
