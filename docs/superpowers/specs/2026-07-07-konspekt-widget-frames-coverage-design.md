# Дизайн: покрытие сегментов и чистка детекции в ветке «виджет с кадрами»

**Дата:** 2026-07-07
**Статус:** одобрен к планированию (учтено ревью Codex)
**Скоуп:** только opt-in ветка «виджет с кадрами» (`layer2_widget.md`, `frames_extract.py`, `frames_schema.json`). Не трогает обычную сборку виджета, master-MD и preview.
**Предшествующая спека:** [`2026-07-02-konspekt-widget-frames-design.md`](2026-07-02-konspekt-widget-frames-design.md) — этот документ дополняет и частично исправляет её.

## Задача

После первого ручного прогона ветки «кадры» обнаружены две проблемы:

1. **Детекция шумная.** Смена ракурса камеры (говорящая голова туда-сюда) по метрике `ffmpeg scene-detect` часто даёт бо́льшую пиксельную дельту, чем реальная смена слайда (плавный переход, слайд занимает часть кадра) — в кандидаты massово проходят повторяющиеся каты одной и той же сцены, а содержательные кадры могут не пройти порог вовсе или быть выброшены при урезке до cap.
2. **Вставка непредсказуема.** Из нарезанных кандидатов в виджет попадает мало картинок, распределение по сегментам случайно: где-то по 2 (потолок), где-то 0. Причина — плоский посегментный/общий потолок (≤2 / ≤12) и позиционная (не по смыслу) урезка кандидатов на Шаге 1, плюс отсутствие механизма, гарантирующего хотя бы один кадр там, где он реально был отснят.

**Важная поправка к предыдущей спеке.** Пункт «вне скоупа» из `2026-07-02-...-design.md` («автоматическая машинная привязка кадр→сегмент по таймкодам сегментов (их нет)») был основан на неверной посылке. У сегментов мастер-MD **есть** обязательный тайминг в шапке (`## Сегмент N | HH:MM:SS-HH:MM:SS | Тема`, формат закреплён в `SKILL.md` §1.4 и парсится в `md_parser.py:332-339`). Аналогичная неточная фраза есть и в `layer2_widget.md` («у сегментов мастер-MD нет собственных таймкодов, машинной синхронизации нет») — обе исправляются в рамках этой задачи.

## Решения

| Развилка | Решение |
|---|---|
| Привязка кадр→сегмент | Детерминированно по таймкоду (парсинг границ сегмента из шапки мастер-MD), не AI-угадывание |
| `segment_hint` в `frames_schema.json` | Убрать — заменяется вычисляемым `segment_id` из `candidates.json` |
| Урезка кандидатов (было cap=60 позиционно) | Посегментные квоты: `dedup_by_gap` применяется внутри каждого сегментного бакета отдельно + общий предохранитель (~150 сырых кандидатов) |
| Шум от повторных катов камеры | Дедуп по содержимому кадра (perceptual hash на PIL, без новых зависимостей) поверх временного дедупа |
| Чувствительность scene-detect | Понизить порог по умолчанию (эмпирически, полагаясь на pHash-дедуп для гашения возросшего шума) |
| Гарантия покрытия сегмента | Для каждого сегментного бакета — обязательный лучший non-drop кандидат в shortlist/full-res, остаток бюджета — по убыванию confidence по всему виджету |
| Посегментный потолок вставки (было ≤2) | Убрать |
| Общий потолок вставки (было ≤12) | Адаптивный: `max(12, число_сегментов + 10)` |
| Вес HTML (≤8 МБ) | Остаётся как есть — единственный жёсткий предохранитель против неограниченного роста |
| Отчёт (Шаг 6) | Добавить разбивку по сегментам: кандидатов / прошло триаж / вставлено |

## Ревью Codex (2026-07-07) — что учтено

Независимое ревью нашло 4 существенные проблемы черновика — все внесены в текст ниже:

1. Порядок «триаж → отбор → full-res» был неявным (риск, что гарантия покрытия конфликтует с идеей shortlist) — зафиксирован явный трёхшаговый порядок в компоненте 5.
2. Адаптивный потолок (15-25 картинок) при фиксированном ≤8 МБ создавал риск позднего отказа без описанной процедуры — добавлен порядок разрешения конфликта в компоненте 6.
3. Дедуп «только с ближайшим по времени» пропускал циклические каты камеры — заменён на скользящее окно N=3 в компоненте 2.
4. Общий предохранитель ~150 был не до конца описан (просто «предупреждение») — заменён на явный fallback-пересчёт квот в компоненте 3.

Некритичные находки (граница до первого/после последнего сегмента, join по `cand_id`, валидация монотонности сегментов, устаревшая фраза в `layer2_widget.md`) — тоже внесены по тексту компонентов 1, 3, 4 и раздела «Обработка ошибок».

## Компоненты

### 1. Границы сегментов (`frames_extract.py`, новое)

Новая функция `segment_bounds(master_md_text) -> list[{'id': '01', 'start': int, 'end': int}]` — сканирует строки `## Сегмент N | HH:MM:SS-HH:MM:SS | ...` тем же паттерном дефиса/en-dash (`[–-]`), что и `md_parser.py:332`, но полностью независимо от него: `md_parser.py` сохраняет только укороченную строку для отображения (`timing`, `_shorten_timing`, строки 338-339), числовых секунд `start`/`end` там нет и не будет — это новый парсинг, не переиспользование существующего.

CLI `frames_extract.py` получает новый обязательный флаг `--master-md <путь>` (нужен для границ сегментов).

**Правила присвоения сегмента кандидату:**
- бакетируем по **исходному обнаруженному таймкоду события** (результат `scene_timecodes`/`cue_timecodes`), а не по фактическому времени извлечённого кадра после сдвига `shift=+0.7` в `extract_frame` — сдвиг нужен только чтобы поймать устоявшийся кадр, к смыслу события он отношения не имеет;
- таймкод раньше начала первого сегмента → первый сегмент; позже конца последнего → последний сегмент;
- таймкод в щели между двумя сегментами (стык, малый зазор) → сегмент с ближайшей границей;
- **валидация входа:** границы сегментов должны быть монотонны, не пересекаться и не быть пустыми (`start < end`, `end[i] <= start[i+1]`) — если мастер-MD этому не удовлетворяет, это ошибка входного контракта (см. «Обработка ошибок»), не тихая деградация.

### 2. Perceptual-hash дедуп (`frames_extract.py`, новое)

После извлечения кадров-кандидатов (как сейчас — по объединённым scene+cue таймкодам, `min_gap=3.0`) — новый шаг `phash_dedup(candidates, threshold=...)`:

- average-hash: PIL `Image.resize((8,8)).convert('L')`, бинаризация по среднему яркости → 64-битная маска;
- сравнение по Hamming-дистанции с **последними N уже оставленными кандидатами** (скользящее окно, например N=3), не только с самым близким по времени — это ловит циклические каты (камера A → камера B → снова камера A), которые пропустил бы дедуп «только с предыдущим»;
- кадры ниже порога дистанции (почти идентичные хоть одному из окна) — гасятся, не доходят до contact-sheet.

**Известное ограничение метода** (не блокер, фиксируется как компромисс): average-hash — грубая метрика. Он может не схлопнуть два кадра одной сцены, различающихся только позой/освещением (ложный «не дубль»), и может ошибочно схлопнуть два слайда с малым отличием в тексте (ложный «дубль»). Конкретные пороги threshold (pHash) и нового (пониженного) `scene-detect threshold` фиксируются как **параметры для эмпирической подгонки** на реальном прогоне — не жёсткие числа в этой спеке. Дефолты в коде выставляются разумным начальным приближением и корректируются по итогам E2E-теста (см. «Тестирование»).

### 3. Посегментные квоты вместо глобального cap

`build_candidates` группирует объединённые scene+cue таймкоды по сегментным бакетам (через `segment_bounds`), затем внутри каждого бакета применяет `dedup_by_gap` независимо (тот же `min_gap=3.0`, локальный cap на бакет — старт с ≤10, подбирается по E2E). Для типичной лекции (5-15 сегментов) это и так держит сумму в разумных пределах (50-150).

**Общий предохранитель — не отдельный «мягкий» механизм, а fallback-пересчёт.** Если сумма после посегментных cap'ов всё равно превышает стартовый дефолт **150** (аномально много сегментов) — посегментный cap **пропорционально уменьшается для всех бакетов одновременно** (не по позиции в общем списке, а тем же способом — `dedup_by_gap` внутри бакета с меньшим cap), пока сумма не впишется в 150. В отчёт (Шаг 6) добавляется предупреждение с итоговым cap на бакет.

`candidates.json` получает новое поле `segment_id` на каждый кандидат.

### 4. Отказ от AI-угадывания сегмента

`frames_schema.json`: поле `segment_hint` удаляется из контракта (было `{"type": ["string", "null"]}`, `required`). Промпты Codex/Sonnet на Шаге 3 (`layer2_widget.md`) больше не просят угадывать сегмент — только `type`, `text`, `caption`, `confidence` (ключ — `cand_id`, он остаётся в контракте).

**Явный контракт join:** после удаления `segment_hint` результат vision-шагов сам по себе не содержит принадлежности сегменту — она восстанавливается склейкой по `cand_id`: главный поток берёт JSON от Codex/Sonnet (по `cand_id`) и джойнит с `candidates.json` (тоже по `cand_id`), откуда достаёт `segment_id`. Это происходит на Шаге 4, до вставки в копию MD.

### 5. Отбор с гарантией покрытия

**Важно про порядок шагов (уточнено по ревью Codex):** двухфазный отбор — это не часть AI-триажа, а детерминированная логика **главного потока** между Шагом 2 и Шагом 3. Меняется роль Шага 2: раньше AI сам решал, какие 5–15 кандидатов войдут в shortlist; теперь AI на contact-sheet **оценивает КАЖДОГО кандидата** (`type` + `confidence`, без отбора) — это уже почти то, что просит нынешний промпт Шага 2 («для КАЖДОГО кандидата поле type... confidence»), нужно лишь явно зафиксировать, что финальный отбор не входит в его ответственность.

Полный порядок:

1. **Шаг 2 (триаж, без изменений в объёме работы).** Codex/Sonnet по contact-sheet оценивает всех кандидатов, включая заведомо шумные — не режет сам, просто скорит `{cand_id, type, confidence}`.
2. **Отбор shortlist (новый, детерминированный, главный поток).** Джойн результата триажа с `segment_id` из `candidates.json` по `cand_id`, затем:
   - **Обязательная фаза.** Для каждого сегментного бакета, где есть хотя бы один кандидат с `type != drop` — берётся кандидат с наибольшим `confidence`. Это гарантированный минимум.
   - **Фаза бюджета.** Оставшийся бюджет (адаптивный потолок минус уже занятое обязательной фазой) заполняется по убыванию `confidence` **по всему виджету целиком**, без оглядки на сегмент — здесь и реализуется «не бояться неравномерности»: у сегмента с 5 хорошими слайдами может оказаться 5 вставленных кадров, у пустого — 0.
3. **Шаг 3 (full-res).** Разбирает только кандидатов, прошедших отбор шага 2 выше — как и раньше, полный контекст (текст/подпись) нужен только для них.

Если у сегмента нет ни одного non-drop кандидата вообще (пусто уже на Шаге 1, либо всё, что было, ушло в drop на триаже) — сегмент законно остаётся без кадра. Это не ошибка и не деградация — таких видео-содержательных моментов там просто не было.

### 6. Лимиты вставки

- Посегментный потолок (было `≤2`) — убирается полностью, отбор регулируется только двухфазной логикой п.5.
- Общий потолок на виджет — адаптивный: `max(12, число_сегментов + 10)`. При типичных 5-15 сегментах это даёт 15-25 — заметно больше прежних 12, поэтому вес HTML перестаёт быть теоретическим ограничением и становится реальным риском (уточнено по ревью Codex).

**Порядок разрешения конфликта «покрытие» vs «вес ≤8 МБ» (новое, отвечает на находку ревью):**
1. Сначала — сильнее сжимать/уменьшать уже отобранные изображения (как предусмотрено в `2026-07-02-...-design.md`, компонент 7): понизить качество JPEG/WebP, уменьшить ширину.
2. Если после максимального сжатия проекция всё равно превышает 8 МБ — убираются кадры из **фазы бюджета** (п.5), по возрастанию `confidence`, начиная с наименее уверенных, пока вес не впишется. Кадры **обязательной фазы** (гарантия ≥1 на сегмент) не трогаются, пока есть что резать из фазы бюджета.
3. Если даже после удаления всех кадров фазы бюджета обязательные кадры одни не вписываются в 8 МБ (крайний случай — очень много сегментов) — деградация с явным предупреждением в отчёте (Шаг 6): какие сегменты лишились гарантированного кадра и почему. Тихого падения сборки быть не должно.

Итоговая сводка ветки дополняется таблицей по сегментам:

Общие числа (найдено / shortlist / вставлено текстом / картинкой / отброшено) остаются как есть, таблица — дополнение, не замена.

## Обработка ошибок (дополнение к существующей деградации)

- Если `--master-md` не передан или в нём не нашлось ни одного `## Сегмент N | HH:MM:SS-...` — явная ошибка (это входной контракт, не опциональная деградация): без границ сегментов гарантия покрытия невозможна в принципе.
- Если границы сегментов немонотонны, пересекаются или пусты (см. валидацию в компоненте 1) — та же категория: явная ошибка с указанием, какие сегменты конфликтуют, а не попытка угадать порядок.
- Если сегментный бакет пуст на Шаге 1 (нет ни scene-, ни cue-кандидата в его диапазоне) — не ошибка, отражается в отчёте нулём.
- Если даже после максимального сжатия и удаления всех кадров фазы бюджета вес превышает 8 МБ (см. компонент 6, п.3) — предупреждение в отчёте с перечнем сегментов, лишившихся гарантированного кадра.
- Прочая деградация (недоступное видео, отсутствие ffmpeg, битый PNG) — без изменений, см. `layer2_widget.md` Шаг 6.

## Тестирование

- **Unit** (`frames_extract`): `segment_bounds` — парсинг диапазонов из мастер-MD с несколькими сегментами (дефис и en-dash), кандидат до первого/после последнего сегмента и в щели между сегментами → корректная привязка; немонотонные/пересекающиеся границы → явная ошибка.
- **Unit** (`frames_extract`): бакетирование по исходному таймкоду события, а не по времени после `shift` в `extract_frame`.
- **Unit** (`frames_extract`): `phash_dedup` — два визуально идентичных кадра (один и тот же фон/поза) гасятся до одного; визуально разные кадры (реальная смена слайда) оба остаются; кадр A похож на кандидата 3 позиции назад (цикл A→B→A) тоже гасится окном N=3, а не только сравнением с предыдущим.
- **Unit** (`frames_extract`): посегментные квоты — кандидаты не теряются из-за глобальной позиционной урезки, когда один сегмент "шумный", а другой — нет; fallback-пересчёт при превышении общего предохранителя 150 уменьшает cap пропорционально всем бакетам.
- **Unit** (двухфазный отбор, главный поток): сегмент с единственным низко-confidence кандидатом всё равно получает его в обязательной фазе; сегмент с 5 кандидатами получает больше 1, если бюджет позволяет; join результата триажа с `segment_id` по `cand_id` корректно восстанавливает принадлежность сегменту.
- **Unit** (вес HTML): при превышении 8 МБ после сжатия сначала режутся кадры фазы бюджета по возрастанию confidence, кадры обязательной фазы остаются последними.
- **Unit** (`frames_schema.json`): валидация, что `segment_hint` больше не в контракте.
- **E2E** (ручной): прогон на реальном уроке с несколькими сегментами и разным визуальным наполнением — проверить глазами: (а) не появляются дубли одного и того же ракурса, (б) хотя бы один слайд на сегмент, где он был отснят, (в) богатый сегмент получает больше одного кадра без искусственного обрезания, (г) отчёт по сегментам совпадает с тем, что видно в виджете. По итогам — подстроить пороги scene-detect/phash (см. компонент 2).

## Вне скоупа (YAGNI)

- Изменение самой сущности scene-detect (например, переход на другой видео-фреймворк вместо ffmpeg) — только тюнинг порога.
- OCR/текстовое распознавание содержимого кадра на этапе дедупа — pHash сравнивает только визуальное сходство, не текст.
- Изменение состава/промптов Codex/Sonnet сверх удаления `segment_hint`.
- Обычная сборка виджета (без кадров), master-MD, preview.
